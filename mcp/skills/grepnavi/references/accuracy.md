# How far to trust each answer

grepnavi resolves symbols from text indexes, not from a compiler. It has no `compile_commands.json`,
no preprocessor evaluation, no type resolution. That buys speed and zero setup on codebases that
cannot be built — and it sets hard limits you must report rather than absorb.

## The engines

Every symbol lookup runs `gtags → ctags → ripgrep` and stops at the first engine that returns
anything. The `engine` field on each hit tells you which one answered.

Measured over 126 sampled kernel symbols across 8 symbol kinds:

| Kind | ctags found it and gtags did not |
|---|---|
| struct member | 15 / 17 |
| struct tag | 9 / 10 |
| union tag | 8 / 13 |
| enum tag | 4 / 15 |
| function / enum constant / typedef | 0–2 |

gtags never found something ctags missed. So: **functions and macros are gtags territory; types and
struct members only exist because ctags is in the chain.** When both engines disagreed (4 cases),
gtags was right — which is why it goes first.

## What no text engine can see

These are invisible to `callers`, `callees`, and `path`. They are not bugs to be fixed; they are the
boundary of the approach:

- **Calls through function pointers.** `pol->pd_alloc_fn(...)` resolves to nothing. `callees`
  returns them apart, under `indirect_calls` with the member `name` and its `receiver`
  (`pol`), and never looks the member name up as a function — that would attach an unrelated
  same-named function with a confidence on it. To see what may be stored there,
  `references(word: name, assign: true)` lists `.name = fn` initializers and `x->name = fn`
  assignments; tables filled positionally or by macros (OpenSSL method tables) stay invisible.
- **Calls generated by macros.** A macro that expands into a call leaves no textual call site.
- **Anything behind a preprocessor condition you did not check.** Text search sees all branches.

So a call tree is **complete for direct calls**, never exhaustive. Say that when the answer matters.
What grepnavi *does* filter out is comment-only mentions, string-literal mentions, and code inside
`#if 0`, so hits are real code.

## Signals to read on every response

| Field | Meaning |
|---|---|
| `index.stale` (from `grepnavi_root`) | Sources are newer than the index. Line numbers may be wrong while looking normal. |
| `truncated: true` | A cap was hit. The list is a sample. Narrow with `dir` / `glob` / a tighter pattern. |
| `engine` | Which index answered. Useful when a result looks off. |
| `confidence: "low"` (callees) | The picked definition may be the wrong one. |
| `likely_trivial` | A well-known primitive (locking, atomics, memcpy, printk). Definition lookup is skipped for these on purpose. |
| `likely_macro` / `likely_non_callable` | Not a real call target. |
| `recommended_for_tree` | `!macro && !non_callable && !trivial` — the simple filter for what to pin. |
| `kind` | `func` / `define` / `struct` / `member` / … A `member` in a callee list means a function pointer. |
| `text` | The source line itself. Classify from this before spending a round trip. |
| `hint` | Present on 0-result responses. Explains the probable cause — read it before saying "not found". |

## Same name, different symbol

C keeps struct tags and functions in separate namespaces, so `struct autofs_dev_ioctl` and
`long autofs_dev_ioctl()` coexist and both come back. Check `kind` against what the user actually
asked about. When the identifier appeared after `struct` / `union` / `enum` in the source, that kind
is ranked first — but candidates are never dropped, because the keyword can still be followed by a
macro that expands to something else.

## Reporting

State the limit alongside the finding, in one clause — not as a disclaimer paragraph:

> `F` is called from 3 places (all in `foo.c`, lines from the `call_line` field). Calls through
> function pointers would not appear here.

> The index was built 6 days ago and sources are newer, so these line numbers may have drifted.

Do not upgrade "no direct chain seen" into "unreachable", or "0 results" into "does not exist".

Never write a `file:line` you did not read out of a tool response. Illustrative examples in this
document deliberately use placeholder names for that reason.

## Discharging the caveat instead of reciting it

The function-pointer caveat is a default, not a verdict. Sometimes you can close it:

- A `static` function can only be called from its own file — the search space is one file.
- For an indirect call to exist, the function's address must be taken somewhere (`.op = F`), and
  that is a textual occurrence. If `grepnavi_search` on the name accounts for every occurrence
  (definition + doc comment + the known call sites) with none being an address-taken assignment,
  there is nowhere for a hidden caller to come from.
- `grepnavi_references` returning the same count as `grepnavi_callers`, with `truncated: false`,
  is independent corroboration.

When you can run that accounting, say so — "complete" is more useful than "complete for direct
calls" when it is actually true. When you cannot, keep the caveat.
